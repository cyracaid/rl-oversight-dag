该先审哪一项？

在一条会传染错误的证据链上，教强化学习把有限的人类注意力花在刀刃上

STA3145 Reinforcement Learning · Group project · 2026-11

Sleep data: 1-year EMA collaboration with Maia ten Brink (Stanford, psychophysiology) · Application: SciForge (Zhangyang Gao, AI4Science)

0一句话

AI 帮我们洗数据、标文献、跑分析。它产出的一条条结果互相依赖：上游错了，下游跟着错，最后结论就不可信。

人不可能全查。所以我们用强化学习学一个建议器：下一步该审哪个节点，让更少的错误走到结论。

人话：这不是训练一个大模型。这是训练一个「该看哪里」的导航仪。机器永远不盖章。

1为什么这个问题是真的

我们实验室的睡眠日记数据：13,990 条记录、237 个人。人只改了 75 处（0.54%）。

但这 75 处不是乱分布的——76% 是同一种错（order_error：时间顺序写反了）。

而且错不会待在原地。时间错了 → 睡眠潜伏期错了 → 睡眠效率错了 → 结论错了。

这就是为什么「审多少」不如「审什么」。预算只有一点点，花在 76% 那种错的上游，比到处乱审值钱。

2我们走过的弯路（诚实版）

第一版我们把它做成「每条独立判断要不要审」的 bandit。结果：

简单阈值赢了 Q-learning（2.81 vs 3.38）。

为什么？因为逐条判断把依赖图压平了，RL 没东西可学。76% 是同一种错，最优策略退化成一条 if 规则。

我们没藏这个失败。它反而是后面重构的理由。

3重构：从「审不审这条」变成「下一个审哪个」

把证据画成一张有向图。智能体在图上走，每一步选一个节点去审。审对了，下游跟着变对。

这是一个真正的 MDP：状态里有图和剩余预算，奖励只在最后给（结论错了几处）。

Front end 划线提问 / 日记行审阅 → 审阅痕迹（不是收据） ↓ Review layer GNN / 贪心 / 阈值 建议器 → 「先审这几个」（只读） ↓ 人点「裁决」 Back end SciForge 证据 DAG + 收据 → 机器不盖章，append-only

8和 OpenAI 两个基准的关系

HealthBench（2025）教我们怎么评：有意义、可信、没饱和，还要报 worst-of-n（一个漏审能作废结论）。

BioBasicsBench（2026-11，湿实验）教我们 everyday science 的失败长什么样：假设压过对照。我们 76% 的 order_error 是同一个物种。

我们采纳：偏学分收据、错误检测当一等技能、「证据还不足以支持结论」当成一个动作。

我们加的、他们没做的：预算 + 依赖图 + 延迟到结论的惩罚。

0One sentence

AI already cleans data, labels papers, runs analyses. Its outputs depend on each other: an upstream mistake poisons the downstream, and the conclusion becomes untrustworthy.

A human cannot check everything. So we train a reinforcement-learning suggester: which node should be reviewed next, so fewer errors reach the conclusion.

In plain words: we are not training a large model. We are training a navigator that says "look here." The machine never stamps.

1Why this problem is real

Our lab's sleep-diary data: 13,990 records, 237 people. Humans corrected only 75 of them (0.54%).

Those 75 are not scattered — 76% are the same mistake (order_error: times written in the wrong order).

And the mistake does not stay put. Wrong time → wrong sleep latency → wrong sleep efficiency → wrong conclusion.

That is why "what to review" matters more than "how much." The budget is tiny. Spending it upstream of the 76% type is worth more than reviewing everywhere.

2The detour we took (honest)

Our first version was a bandit: "review this item or not," one at a time. Result:

A simple threshold beat Q-learning (2.81 vs 3.38).

Why? Per-item review flattens the graph. RL had nothing non-trivial to learn. With 76% one type, the best policy collapses into an if-rule.

We did not hide this failure. It is the reason for the reframe.

3Reframe: from "review this item?" to "which node next?"

Draw the evidence as a directed graph. The agent walks the graph and picks one node to review. A good review changes the downstream.

This is a real MDP: the state has the graph and the remaining budget; the reward arrives only at the end (how many conclusions are still wrong).

Front end highlight-and-ask on diary rows / code / claims → review traces (not receipts) ↓ Review layer GNN / greedy / threshold suggester → "review these first" (read-only) ↓ human clicks "verdict" Back end SciForge evidence DAG + receipts → machine never stamps, append-only

DQN degenerates to random — a sparse terminal reward cannot feed a value function. That is why policy gradient is the right tool here.

8How this relates to OpenAI's two benchmarks

HealthBench (2025) taught us how to evaluate: meaningful, trustworthy, non-saturated, and report worst-of-n (one missed error can invalidate a conclusion).

BioBasicsBench (2026-11, wet lab) showed what everyday-science failure looks like: an assumption overriding a control. Our 76% order_error is the same species.

We adopt: partial-credit receipts, error detection as a first-class skill, and "the evidence is not enough yet" as an explicit action.

We add what they did not build: a budget, a dependency graph, and a penalty delayed to the conclusion.

  • The suggester is read-only on the evidence graph. It outputs a ranking.
  • A receipt exists only when a human clicks "verdict."
  • A suggestion never becomes a verdict automatically.
  • The real raw data (13,990 rows, 75-row CSV) never enters git.

0한 문장

AI가 데이터를 정제하고, 문헌에 라벨을 달고, 분석을 돌립니다. 그 출력은 서로 의존합니다: 상류가 틀리면 하류도 틀리고, 결론이 믿을 수 없게 됩니다.

사람이 전부 확인할 수는 없습니다. 그래서 강화학습으로 제안기를 학습합니다: 다음에 어떤 노드를 검토할지, 결론에 도달하는 오류를 줄이기 위해서.

쉽게 말하면: 큰 모델을 학습하는 게 아닙니다. "여기를 봐라"라고 말하는 내비게이션을 학습하는 겁니다. 기계는 도장을 찍지 않습니다.

1왜 진짜 문제인가

우리 실험실 수면 일기 데이터: 13,990 기록, 237명. 사람이 고친 것은 75건(0.54%)뿐입니다.

그 75건은 흩어져 있지 않습니다 — 76%가 같은 실수(order_error: 시간 순서가 반대로 쓰임)입니다.

그리고 실수는 제자리에 머물지 않습니다. 시간이 틀리면 → 수면 잠복기가 틀리면 → 수면 효율이 틀리면 → 결론이 틀립니다.

그래서 "얼마나 검토하느냐"보다 "무엇을 검토하느냐"가 중요합니다. 예산은 아주 작습니다. 76% 유형의 상류에 쓰는 것이 아무데나 검토하는 것보다 값집니다.

2우리가 돌아간 길 (솔직하게)

첫 버전은 밴딧이었습니다: "이 항목을 검토할까 말까"를 하나씩. 결과:

간단한 임계값이 Q-러닝을 이겼습니다 (2.81 vs 3.38).

왜? 항목별 검토는 그래프를 평평하게 만듭니다. RL은 배울 비자명한 것이 없었습니다. 76%가 한 유형이라 최적 정책은 if-규칙으로 무너집니다.

이 실패를 숨기지 않았습니다. 재구성의 이유입니다.

3재구성: "이 항목을 검토할까?"에서 "다음 노드는?"으로

증거를 방향 그래프로 그립니다. 에이전트가 그래프를 걷고 노드를 하나 골라 검토합니다. 좋은 검토는 하류를 바꿉니다.

이것은 진짜 MDP입니다: 상태에는 그래프와 남은 예산이 있고, 보상은 마지막에만 옵니다(결론이 몇 개나 아직 틀린지).

Front end 일기 행 / 코드 / 주장에 하이라이트-질문 → 검토 흔적 (영수증 아님) ↓ Review layer GNN / 탐욕 / 임계값 제안기 → "이것 먼저 검토" (읽기 전용) ↓ 사람이 "판정" 클릭 Back end SciForge 증거 DAG + 영수증 → 기계는 도장을 찍지 않음, append-only
