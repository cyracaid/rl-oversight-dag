# 我们自己的审计链：最小可行版

> 目标只有一个：**把「审阅次数」换算成「审阅分钟」**。
> 不是为了合规，不是为了链上存证，是为了回答一句「每抓一个真错，人类花了多久」。
> 现在这句话我们答不了——睡眠侧 75 条纠错里只有 1 条有 `resolved_at`。

---

## 1. 收据长什么样

一条收据 = **一次提交**。不是一次点击，不是一次停留，不是一次会话。

```jsonc
{
  "schema": "review.receipt.v1",
  "event_id": "uuid",
  "artifact_version": "sha256:…",     // 审的是哪个不可变版本
  "field_path": "TIME_AWAKE",         // 粒度；多字段用 "+" 连接（沿用你们 M1_viol_pairs 的写法）
  "row_key": "sha256:…",              // 行的内部键哈希，不存原始 pid
  "actor": "sha256:…",                // 审阅者哈希
  "opened_at": "2026-11-09T09:00:00Z",// 打开该条目的时间
  "submitted_at": "2026-11-09T09:01:02Z",
  "verdict": "corrected",             // corrected | accepted | rejected | skipped
  "reason_code": "order_error",       // 可选：错误类型
  "prev": "sha256:…",                 // 上一条的摘要，链式
  "digest": "sha256:…"                // 本条摘要
}
```

`duration` 不单独存——由 `submitted_at - opened_at` 导出。存两个时间戳而不是一个时长，是因为时长丢了就再也拆不回来了。

## 2. 五条规则

| 规则 | 为什么 |
|---|---|
| **append-only** | 改判＝写一条新收据，旧的不动。否则「当时的顺序」会被事后重写 |
| **一动作一条** | 只记提交。点击/滚动/停留都不记，否则事件量爆炸、时长被污染 |
| **只记 id，不记内容** | 不要正文、不要参与者信息、不要自由文本备注 |
| **`prev` 链** | 删一行、换顺序都能被发现，成本几乎为零，不需要服务器 |
| **字段粒度** | `field_path` 能到字段就写字段；写不了就留空，自动退化成行级 |

## 3. 写在哪里

**不要**塞进 `knowledge-net`——那是阅读记录域，语义不对。
三个可选落点，按推荐顺序：

1. **`artifact-versions` 的 commit 路径**（推荐）：版本本来就有 `createdAt` + `actor`，只需补 `field_path`、`opened_at`。
2. **`evidence-dag` 的 producer-receipt**：如果审阅动作本身会产生一条 producer 回执，把这三个值挂上去。
3. **独立 JSONL**（我们这边已经实现）：审阅界面提交时 append 一行，零依赖，随时可换。

## 4. 现有数据能回填多少

| 字段 | 现状 | 能否回填 |
|---|---|---|
| `artifact_version` | ✅ 有 | — |
| `actor` | ✅ 有 | — |
| `createdAt` | ✅ 有 | — |
| `submitted_at` | ⚠️ 近似等于 `createdAt` | 只能近似 |
| `opened_at` | ❌ 无 | **不能** |
| `field_path` | ❌ 无 | **不能** |
| `verdict` | ❌ 无（capability 的 approval 不是判决） | **不能** |

所以：**顺序可以从现有数据近似重建，人时不能。** 三个值必须新记。

## 5. 评估契约：收据怎么变成结论

```
receipts ──► 每个字段的中位耗时 t̄
           ──► 每次审阅的代价 c = |field_path| × t̄
           ──► 按策略排序后累计 c，得到 recall @ minutes
```

已经跑通（`run_audit_demo.py`，200 条收据，链校验通过，中位 62 秒/条）：

| 审阅预算 | 整行（读 4 个字段） | 只读 witness 对（2 个字段） |
|---|---:|---:|
| 60 min | 8.8% | **25.0%** |
| 120 min | 25.0% | **63.2%** |
| 240 min | 63.2% | **83.8%** |

| 目标召回 | 整行 | 只读 witness 对 |
|---|---:|---:|
| 25% | 115 min | **58 min** |
| 50% | 195 min | **98 min** |
| 75% | 279 min | **139 min** |

每字段 30 秒是**假设**，比率不是。真实收据一到，把中位数代进去，整张表按比例缩放，结论不变。

## 6. 降级阶梯（如果只能做到一部分）

| 能记到 | 我们能报 | 论文里怎么说 |
|---|---|---|
| 字段 + 两个时间戳 | 每错误人时、field 级召回 | 完整 impact |
| 行 + 两个时间戳 | 每错误人时、行级召回 | impact 有，粒度粗 |
| 行 + `createdAt` | 「到下一次提交的间隔」的弱代理 | 明确标注是间隔，不是耗时 |
| 只有次数 | 每错误次数 | 不说人时 |

每降一档，少一个指标，但论文都能写——只是局限段多一句。**不要为了完整而等，先拿最粗的那一档。**

## 7. 隐私红线

- `row_key` 和 `actor` 只存哈希，盐由自己持有；
- 收据里永不出现原始 pid、日期、时间值、备注；
- 导出给外部前先跑一遍 `verify_chain`，并只给聚合量；
- 收据本身也在 `.gitignore` 范围内（`outputs/*.jsonl` 不进仓库）。

## 8. 上线清单（估计一天）

1. 定 `artifact_version` 的取法（版本 id 还是内容摘要）。
2. 审阅界面在「打开」和「提交」各打一个点，写进 `opened_at` / `submitted_at`。
3. 提交时带出高亮字段 → `field_path`；多字段用 `+` 连接。
4. 接上 `audit/receipts.py`（append + 链校验），先跑影子模式：只记不读。
5. 一周后对比：`duration` 的中位数是否合理（<5s 说明打点错了，>2h 说明被打断，需要上限）。
6. 把中位数代进 `run_audit_demo.py`，出第一张真实的 recall@minutes。

## 9. 已知陷阱

- **打断**：审到一半去开会，`duration` 会是几小时。设 15 分钟上限并打 `interrupted` 标记，别默默截断。
- **一次提交改多个字段**：一条收据 + `field_path` 用 `+` 连接，不要拆成多条（拆了会重复计时）。
- **重开同一条**：算两次审阅，第二次的 `opened_at` 是新的一次——这是对的，别去重。
- **把「打开」当事件计数**：会稀释分母。只对提交计数。
